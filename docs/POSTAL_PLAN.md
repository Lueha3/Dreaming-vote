# 기업용 우편번호 조회 도구 — 기획 및 개발 계획

집 주소 리스트를 붙여넣으면 도로명·지번·우편번호를 한꺼번에 변환해주는 도구.
수만 건을 짧은 시간에 처리하고, 결과를 드래그 한 번으로 엑셀에 복사한다.

## 설계를 좌우한 판단 3가지

1. **수만 건 = 공공 API 불가.** 건별 호출은 쿼터·속도 모두 못 버틴다. 행안부가 무료
   배포하는 **도로명주소 DB 전체분**(건물 단위, 도로명·지번·우편번호 포함, 상업 이용 가능)을
   통째로 받아 자체 Postgres 로 만든다. → 수만 건도 수십 초 내.
2. **진짜 난이도는 조회가 아니라 정제.** 붙여넣는 주소는 더럽다(서울/서울시/서울특별시,
   123-4 vs 123번지 4호, 동호수·괄호 섞임, 오타). **매칭률 = 제품 경쟁력.**
3. **우편번호→주소는 1:N.** 우편번호 하나에 건물 수백. "우편번호만 넣으면 주소 하나"는 불가능.
   → **대표주소 + 외 N건**으로 스펙 확정.

## 스펙

- 입력: 한 줄에 주소 하나. 유형(우편번호/도로명/지번)은 **자동 판별** — 사용자가 모드 선택 불필요.
  - 5자리 숫자 → 우편번호 → 도로명·지번(대표) 반환
  - `로/길/대로 + 번호` → 도로명 → 지번·우편번호 반환
  - 그 외 → 지번 → 도로명·우편번호 반환
- 출력 표: `원본 | 도로명주소 | 지번주소 | 우편번호`. 실패 행은 빨강, 여러건은 노랑.
- **전체 복사**(탭 구분 TSV → 엑셀 열에 딱 맞음), **실패만 복사** 별도.
- 로그인·파일 업로드 없음. 화면 1개, 큰 버튼 2개(변환하기 / 전체 복사).

## 아키텍처

```
[브라우저]  붙여넣기 → 유형 판별 → 정규화 → 매칭 → 표/복사
             │
             ├─ 데모/수천 건: 클라이언트에서 즉시 (샘플 DB 번들, 청크+진행바)
             └─ 운영/수만 건~전국: /api/postal/convert → Postgres(PostalBuilding)
```

핵심 순수 로직은 `src/lib/postal/` 에 프레임워크 독립적으로 구현 → 클라이언트/서버 공용,
단위 테스트로 매칭률 회귀 검증.

| 파일 | 역할 |
|---|---|
| `lib/postal/normalize.ts` | **정제 엔진**(시도 통일·번지 표기·괄호/동호수 제거) + 매칭 키 생성 |
| `lib/postal/detect.ts` | 줄 유형 자동 판별 |
| `lib/postal/match.ts` | 입력→키→store 질의→결과 구성 (1:N 처리 포함) |
| `lib/postal/store.ts` | `AddressStore` 인터페이스 + 메모리 구현(운영은 Postgres 로 교체) |
| `lib/postal/index.ts` | 일괄 변환 · TSV 직렬화 · 통계 |
| `app/postal/page.tsx` | 할머니 기준 UI(청크 처리 + 진행바 + 복사) |
| `app/api/postal/convert/route.ts` | 서버 일괄 변환(운영 확장 지점) |
| `scripts/postal/load-juso.ts` | 행안부 전체분 → Postgres COPY 대량 적재 |
| `prisma/schema.prisma` | `PostalBuilding`(zipcode/roadKey/jibunKey 인덱스) |

## 개발 단계

- **0단계 (완료 이 커밋):** DB 스키마(`PostalBuilding`) · 적재 스크립트 · 정규화/판별/매칭
  엔진 + 단위 테스트 · 샘플 데이터로 동작하는 UI. → **붙여넣기→변환→복사** 전 과정 데모 가능.
- **MVP (다음):** 행안부 전체분 실제 적재 → 물류 현장의 진짜 더러운 리스트로 매칭률 검증.
  API 라우트의 `store` 를 Postgres 백엔드로 교체.
- **v1:** 유사매칭·오타 보정(건물명·부분일치 스캔은 `MemoryStore.scan` 에 원형 구현됨),
  실패 리포트. **목표 매칭률 95%+.**
- **v2:** 월간 자동 갱신 배치, 엑셀 파일 업로드, 사업화(사용량 요금제·API 판매).

## 실제 데이터 적재 방법

1. https://business.juso.go.kr → 주소DB → **도로명주소 한글(전체분)** 다운로드(무료).
2. 압축 해제한 `주소_*.txt`(파이프 구분, EUC-KR)를 한 폴더에 모은다.
3. 스키마 반영: `npx prisma migrate dev`(또는 `prisma db push`)로 `PostalBuilding` 생성.
4. 적재 의존성: `npm i pg pg-copy-streams && npm i -D iconv-lite tsx`.
5. `DATABASE_URL` 설정 후 `npx tsx scripts/postal/load-juso.ts ./juso_data`.
   - `scripts/postal/load-juso.ts` 상단 `COLS` 매핑을 배포본 레이아웃 문서로 확인·조정.
6. API `store` 를 `MemoryStore` → Postgres 질의 구현으로 교체
   (인덱스가 있으므로 `WHERE roadKey = $1` 형태 그대로).

## 리스크

1. **정제 로직 매칭률** (공수의 70%) — 실데이터 반복 튜닝으로만 올라감.
2. **우편번호 1:N 스펙 합의** — 대표+외 N건으로 확정.
3. **차별화** — "붙여넣기 한 번"의 단순함·속도.
